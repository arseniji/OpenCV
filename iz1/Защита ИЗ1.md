# Как устроено наше ИЗ по слежению за объектом

Если открываешь проект впервые, сначала прочитай постановку, затем пройди [`car2` по шагам](#один-ролик-от-архива-до-графика). Если уже готовишься показывать работу, переходи к [запуску](#как-запустить-у-себя) и [разбору ошибок](#семь-эпизодов-которые-можно-показать).

## Что мы вообще делаем

Представь видео с велосипедистом. На первом кадре тебе показывают прямоугольник вокруг него. На втором кадре он уже чуть правее, на третьем стал крупнее, а потом его может перекрыть другой предмет. Задача программы — ставить рамку вокруг **того же велосипедиста** на каждом следующем кадре.

Рамка в коде — это четыре числа `(x, y, w, h)`. `x, y` — левый верхний угол, `w, h` — ширина и высота. В эталонной разметке такая рамка уже записана для кадров, где положение объекта известно. **Трекер получает из разметки только первую рамку.** Остальные нужны позже, чтобы сравнить ответы программы с эталоном. Это и есть OPE — один непрерывный прогон с одной инициализацией. Если трекер потерял объект, он всё равно получает следующие кадры.

Мы прогнали CSRT, KCF, MOSSE и Лукаса–Канаде, а ещё сделали свой вариант Лукаса–Канаде с изменением размера рамки. Видео взяли из UAV123. `dev` — шесть фрагментов для экспериментов и подбора параметра, `test` — ещё шесть для итоговой проверки. Это 2 884 и 2 650 кадров соответственно. Например, на `dev` можно проверить три настройки и выбрать одну. На `test` запускаешь уже выбранную настройку и смотришь, перенёсся ли результат на другие видео. [Официальный UAV123](https://ivul.kaust.edu.sa/benchmark-and-simulator-uav-tracking-dataset)

## Как читать проект

Держи в голове цепочку. Подготовили кадры → проверили данные → прогнали трекеры → посчитали метрики → нарисовали графики и рамки. Если хочешь понять сам алгоритм, начни с `run_trackers.py`, а из него переходи в `trackers.py` и `student.py`.

### Сначала готовим данные

| Файл | Что в нём смотреть |
| --- | --- |
| [`config.json`](config.json) | Список видео, исходные папки и число кадров. Например, запись `"car1_1": ["car1", 500]` означает, что фрагмент `car1_1` берём из папки `car1`, первые 500 кадров. `opencv_threads: 1` задаёт один поток OpenCV для сравнения скорости. |
| [`protocol.py`](protocol.py) | Общие настройки, которые импортируют остальные скрипты. Здесь читается `config.json`, находятся папки `data` и `results`, перечисляются методы и задаются условия проверки на уменьшенной яркости и размере. |
| [`prepare_data.py`](prepare_data.py) | Достаёт выбранные JPG и разметку из ZIP. Для координат `x, y` вычитает единицу, потому что в исходной разметке отсчёт идёт с единицы, а в OpenCV — с нуля. Записывает `groundtruth.csv` и `manifest.json` со списком исходных кадров. |
| [`remote_zip.py`](remote_zip.py) | Нужен для `--download`. Python может читать удалённый ZIP как обычный файл: `seek` меняет позицию, `read` забирает нужный диапазон байтов. Сервер отвечает `206 Partial Content`. Так можно получить выбранные кадры, не сохраняя весь архив на 13 ГБ. С локальным `--archive` этот механизм не используется. |
| [`audit.py`](audit.py) | Сверяет имена видео, номера кадров и длину разметки. Проверяет, что исходная папка видео целиком попала в одну часть и что между частями нет побайтово одинаковых JPG. С `--freeze` ещё сохраняет выбранную настройку и SHA‑256 файлов в `submission.json`. |

### Тут реально идёт слежение

**[`run_trackers.py`](run_trackers.py)** — главный файл запуска. Открой `run_sequence`. Он читает одну строку `groundtruth.csv`, открывает `000001.jpg` и создаёт по одному трекеру на каждый выбранный метод. Первый кадр сразу записывается с заданной рамкой и нулевым временем обновления. Дальше цикл идёт со второго кадра. Для каждого метода вызывается `tracker.update(frame)`, замеряется время, а результат добавляется в отдельный CSV. Если метод вернул `None`, четыре координаты записываются как `nan`. Цикл при этом продолжается. На тесте скрипт сверяет выбранный параметр, контрольные суммы и данные с файлом фиксации. Уже сохранённые тестовые CSV пропускает.

**[`trackers.py`](trackers.py)** содержит два класса. `OpenCVTracker` — обёртка над готовыми CSRT, KCF и MOSSE. У всех одна схема вызова: `init` получает первый кадр и рамку, `update` получает следующий кадр. Класс `LucasKanade` уже описывает логику нашей базовой версии. В `detect` ищутся точки внутри рамки, в `propagate` вычисляются их новые координаты, в `move` рамка сдвигается на медиану смещений. В `update` нужно хотя бы три годных пары для ответа. Когда осталось меньше 12 точек, класс ищет новые в текущей области.

**[`student.py`](student.py)** — наша доработка. `ScaleLucasKanade` наследует базовый класс и меняет только `move`. Отбор и перенос точек остаются теми же. Вместо одного сдвига по точкам оцениваем ещё изменение масштаба. Если модель плохо согласуется с точками или масштаб слишком резко изменился, вызываем обычный `move` родительского класса. На защите можно буквально открыть два метода `move` рядом и показать, чем они отличаются.

### Здесь проверяем результаты и оформляем их

| Файл | Что в нём смотреть |
| --- | --- |
| [`metrics.py`](metrics.py) | `evaluate_sequence` берёт две последовательности рамок и считает для каждого кадра ошибку центра и IoU. Из этих массивов получаются P20, AUC и интервалы срывов. Здесь смотреть, что происходит на граничных значениях порогов. |
| [`evaluate.py`](evaluate.py) | Читает готовые CSV трекеров и эталон. Вызывает `metrics.py` для каждой пары «видео и метод». Собирает результаты по видео и общую таблицу. Здесь рассчитывается итоговый FPS. Сам трекер на этом этапе не запускается. |
| [`robustness.py`](robustness.py) | Работает на `dev`. С `--tune` проверяет ограничения масштаба 1,03, 1,06 и 1,10. Потом сравнивает методы на исходных кадрах, при яркости 70% и при размере 75%. Подбор пишет в `tuning.csv`, проверку устойчивости — в `robustness.csv`. |
| [`report.py`](report.py) | Берёт уже рассчитанные результаты, строит precision и success, рисует рамки и собирает MP4. Зелёная рамка — эталон, оранжевая — ответ трекера. Для срыва показывает кадр перед началом, начало и кадр внутри эпизода. |
| [`tests/test_protocol.py`](tests/test_protocol.py) | Маленькие проверки без скачивания UAV123. В том числе проверяется IoU на пороге, срыв через кадр без разметки, перенос рамки Лукаса–Канаде и обратный пересчёт координат после уменьшения изображения. Это тесты кода. Выборка `test` — реальные фрагменты UAV123. |

Остальные файлы нужны вокруг эксперимента. [`requirements.txt`](requirements.txt) фиксирует версии NumPy, OpenCV Contrib и Matplotlib. [`.gitignore`](.gitignore) перечисляет локальные данные, результаты и окружения, которые не надо отправлять в Git. [`README.md`](README.md) содержит короткие команды. [`submission.json`](submission.json) — сохранённая фиксация перед итоговым прогоном. В `data/` лежат входные JPG и эталон. В `results/` лежат ответы, метрики и картинки. Например, [`car2_STUDENT.csv`](results/test/predictions/car2_STUDENT.csv) — траектория одного метода по кадрам, [`per_sequence.csv`](results/test/per_sequence.csv) — качество отдельно по каждому видео, [`summary.csv`](results/test/summary.csv) — сводка по методам. DOCX — отчёт, ZIP — комплект для сдачи. `.venv310` — рабочее окружение с пакетами. В `.tools/python` находится сам интерпретатор Python 3.10, на который ссылается это окружение.

## Один ролик от архива до графика

Возьмём `car2`. Это тестовый фрагмент с машиной. Открой код, данные и готовый результат рядом. Ниже порядок, в котором скрипты передают друг другу данные.

```text
config.json + Dataset_UAV123.zip
        ↓ prepare_data.py
data/test/car2/{кадры JPG, groundtruth.csv}
        ↓ audit.py → submission.json
        ↓ run_trackers.py → trackers.py / student.py
results/test/predictions/car2_STUDENT.csv
        ↓ evaluate.py → metrics.py
per_sequence.csv + summary.csv + curves.json + failures.json
        ↓ report.py
графики PNG, эпизоды срыва PNG и видео MP4
```

1. **Выбираем вход.** В `config.json` запись `"car2": ["car2", 500]` задаёт исходную папку и длину. `prepare_data.py` ищет в ZIP кадры `data_seq/UAV123/car2/000001.jpg` и далее, отдельно ищет `anno/UAV123/car2.txt`. Он сначала проверяет, что кадры и строки разметки на месте, затем пишет входы в `data/test/car2`. В `data/test/manifest.json` остаются источник и номера выбранных кадров.
2. **Проверяем состав.** `audit.py` сверяет список файлов с ожидаемыми номерами, проверяет форму разметки `(500, 4)` и первую рамку. Для поиска побайтовых повторов запоминает, в какой части впервые встретился SHA‑256 JPG. Также проверяет, что один исходный каталог не попал в обе части, даже если его фрагменты называются по-разному. При фиксации сохраняет контрольные суммы корневых `.py`, `config.json` и `requirements.txt`, хеш разметки и хеш последовательности кадров для каждого видео. Близкие по содержанию JPG с разными байтами такой проверкой не выявляются.
3. **Начинаем слежение.** В `run_sequence` у чтения разметки стоит `max_rows=1`. Первый кадр и рамка передаются каждому методу при создании объекта-трекера. Затем цикл начинается с `2`, а `update(frame)` получает только очередной кадр. Состояние живёт внутри объекта-трекера. Например, LK хранит предыдущий полутоновый кадр, набор точек и текущую рамку.
4. **Записываем ответ.** На втором кадре STUDENT получил рамку примерно `(689.85, 366.67, 35.97, 20.98)`. В CSV рядом записалось `0.0045743` секунды, то есть примерно 4,57 мс на этот вызов `update`. Это один замер. Скорость метода в итоговой таблице рассчитывается по всем обновлениям во всех фрагментах части. [Покадровый CSV car2](results/test/predictions/car2_STUDENT.csv)
5. **Сравниваем с эталоном.** `evaluate.py` находит ту же строку в полном `groundtruth.csv`. На втором кадре там `(690, 366, 36, 21)`. Ошибка центра около 0,68 пикселя, IoU около 0,930. Кадр проходит и P20, и порог IoU ≥ 0,5. На кадре 153 картина другая: центр всё ещё в пределах P20 с ошибкой 17,22 пикселя, а IoU уже 0,099914. Именно здесь начинается непрерывный срыв по IoU.
6. **Смотрим своими глазами.** `report.py` снова открывает JPG и наносит на него обе рамки из сохранённых данных. По `failures.json` он знает, с какого кадра показать ошибку. Графики берёт из `curves.json`. Надпись с названием метода и номером кадра добавляется при сборке видео. Видео проигрывается с частотой 30 кадров/с. Это скорость воспроизведения, а 16,8 кадра/с у CSRT в сводке — измеренная скорость работы алгоритма. [Видео результата](results/test/videos/car2_STUDENT.mp4)

### Почему у нас сразу несколько CSV и JSON

| Где смотреть | На какой вопрос отвечает |
| --- | --- |
| `data/test/car2/groundtruth.csv` | Где машина по разметке? По строке на кадр, без заголовка и отдельного столбца номера. |
| [`car2_STUDENT.csv`](results/test/predictions/car2_STUDENT.csv) | Где её увидел STUDENT и за какое время? Есть номер кадра, четыре координаты и время. |
| [`per_sequence.csv`](results/test/per_sequence.csv) | Как метод прошёл конкретное видео целиком? Есть, например, отдельная строка для `car2` и `STUDENT`. |
| [`summary.csv`](results/test/summary.csv) | Как метод прошёл всю часть? По одной строке на метод. |
| [`curves.json`](results/test/curves.json) | Какие значения ставить на графики precision и success для каждого порога? |
| [`failures.json`](results/test/failures.json), [`examples.json`](results/test/examples.json) | В первом все найденные интервалы срывов с покадровыми IoU. Во втором — отобранные примеры и ссылки на картинки. |
| [`selection.json`](results/dev/selection.json), [`submission.json`](submission.json) | В первом решение по итогам подбора на `dev`. Во втором — копия решения вместе с контрольными суммами кода и данных перед `test`. |

У покадрового CSV разделитель — запятая. В итоговых таблицах используется `;`, а заголовок сохранён в UTF‑8 с BOM, чтобы его было удобнее открывать в табличном редакторе. В Python `np.loadtxt()` для этих типов файлов будет вызываться с разными `delimiter`.

## Какая теория реально нужна

**Лукас–Канаде и оптический поток.** Представь тёмный угол окна машины. Его можно узнать в соседнем кадре по тому, как меняется яркость вокруг него. На однотонном асфальте таких ориентиров меньше. Поэтому `goodFeaturesToTrack` ищет точки с заметным изменением яркости в двух направлениях. `calcOpticalFlowPyrLK` оценивает, куда каждая точка сдвинулась между кадрами. Пирамида — это несколько уменьшенных версий кадра: крупное смещение сначала проще найти на грубом масштабе, затем уточнить на более подробном. Базовый LK собирает смещения точек и берёт медиану отдельно по `x` и `y`. Если точки дали по `x` значения `4, 5, 5, 6, 80`, медиана будет `5`. Один улетевший за объект ориентир не перетянет за собой всю рамку. [Разбор оптического потока в документации OpenCV](https://github.com/opencv/opencv/blob/5.x/doc/tutorials/others/optical_flow.markdown)

**RANSAC и оценка масштаба.** Обычный LK может передвинуть рамку, даже если машина при этом выросла в кадре. В нашей доработке `estimateAffinePartial2D` пытается найти преобразование, которое объясняет переход от старых точек к новым: единый масштаб, поворот и перенос. RANSAC примеряет модели по небольшим подмножествам точек и проверяет, сколько пар с ними согласуется. У нас допуск для пары — 2 пикселя, а согласоваться должны хотя бы три пары и не меньше половины всех пар. Из матрицы берём масштаб и новое положение центра. Ширину и высоту умножаем на один коэффициент, а сама рамка остаётся параллельной краям изображения. При `s = 1,10` разрешён масштаб от `1/1,10` до `1,10` за один шаг. Важная деталь: даже небольшое лишнее увеличение может накопиться, потому что размеры обновляются на каждом кадре.

**CSRT, KCF и MOSSE.** Для защиты достаточно общей идеи корреляционного фильтра. По начальной рамке строится модель внешнего вида объекта. На новом кадре фильтр даёт карту отклика в области поиска, а сильный отклик подсказывает новое положение. MOSSE обучает простой адаптивный фильтр по квадрату ошибки отклика. KCF использует ядерную модель и структуру сдвигов, чтобы эффективно считать такой отклик. CSRT учитывает надёжность разных участков объекта и каналов признаков. Проще говоря, он может меньше полагаться на часть рамки, которая плохо помогает узнать объект. Все три реализации мы вызываем из OpenCV Contrib. [Статья MOSSE](https://doi.org/10.1109/CVPR.2010.5539960), [статья KCF](https://arxiv.org/abs/1404.7584), [статья CSRT](https://openaccess.thecvf.com/content_cvpr_2017/html/Lukezic_Discriminative_Correlation_Filter_CVPR_2017_paper.html)

**Как читать метрики на защите.** P20 — доля размеченных кадров, где центры рамок разошлись максимум на 20 исходных пикселей. IoU учитывает всю рамку: площадь пересечения делим на площадь объединения. Можно идеально попасть в центр огромной рамкой и всё равно получить низкий IoU. На `wakeboard2` у CSRT P20 был 91,6%, а доля кадров с IoU ≥ 0,5 — 7,0%. Из одного P20 точность размеров не видна.

- **Precision** — доля попаданий при разных порогах ошибки центра. **Success** — доля кадров с IoU строго выше выбранного порога. **AUC** в этом проекте — среднее по 21 точке success от 0 до 1 с шагом 0,05. Отдельный показатель «IoU ≥ 0,5» включает равенство.
- **Срыв** — непрерывный кусок с IoU < 0,1. Если на кадре есть эталон, а трекер не выдал рамку, IoU считаем нулём, ошибку центра — бесконечной. Кадр без эталона не входит в знаменатель метрик и разрывает эпизод срыва. Первый инициализационный кадр входит в метрики качества.
- **FPS** считаем как число вызовов `update`, делённое на суммарное время этих вызовов. Сюда не входит чтение кадров и рисование. Среднее FPS по роликам дало бы другую величину. Быстрый отказ тоже считается вызовом, поэтому высокий FPS сам по себе мало говорит о качестве.
- **При уменьшении кадра** возвращаем координаты в исходный размер по фактическим коэффициентам ширины и высоты. Иначе порог 20 на кадре, сжатом до 75%, означал бы примерно 26,7 исходного пикселя.

### Если попросят объяснить математику и настройки

**Откуда берётся смещение у LK.** Берём яркость окрестности точки. Между соседними кадрами считаем, что соответствующие пиксели сохраняют близкую яркость и что маленький участок движется примерно одинаково. Если обозначить яркость буквой `I`, локально получаем условие `Ix·u + Iy·v + It ≈ 0`. `Ix` и `Iy` — изменения яркости по горизонтали и вертикали, `It` — изменение между кадрами. `u, v` — искомое смещение. Один пиксель даёт одно уравнение на две неизвестные. Лукас–Канаде берёт целое окно и подбирает смещение методом наименьших квадратов. На прямой границе трудно понять движение вдоль неё, а у угла яркость меняется в двух направлениях. Поэтому в `detect` мы ищем угловые точки методом Ши–Томаси через `goodFeaturesToTrack`. [Теория и пример в OpenCV 4.12](https://docs.opencv.org/4.12.0/d4/dee/tutorial_optical_flow.html)

**Какие числа в `trackers.py` за что отвечают.** В `goodFeaturesToTrack(..., 100, 0.01, 3)` просим до 100 точек, задаём относительный порог качества 0,01 и минимум 3 пикселя между точками. Поиск идёт внутри вырезанной области, поэтому потом прибавляем `x0, y0`, чтобы вернуть точки в координаты целого кадра. `calcOpticalFlowPyrLK` возвращает оценку новых точек и `status`. Берём те, для которых `status = 1` и координаты остались внутри изображения. Отметка `1` говорит, что OpenCV нашёл соответствие. Она сама по себе не доказывает, что точка всё ещё принадлежит объекту.

**Как из матрицы получается размер рамки.** Для единого масштаба `s` и угла `θ` первый столбец матрицы содержит `s·cos(θ)` и `s·sin(θ)`. Его длина равна `s`, поэтому в `student.py` используется `np.hypot(matrix[0, 0], matrix[1, 0])`. Новый центр берётся по формуле `A @ center + t`, где `A` — первые два столбца, `t` — последний. После изменения `w, h` вычитаем половину нового размера из нового центра и получаем левый верхний угол. [Матрица `estimateAffinePartial2D` в OpenCV 4.12](https://docs.opencv.org/4.12.0/d9/d0c/group__calib3d.html)

**Как руками прикинуть IoU.** Пусть две рамки размера `12 × 10` сдвинуты на 6 пикселей по горизонтали. Перекрытие `6 × 10 = 60`. Объединение `120 + 120 − 60 = 180`. Значит, IoU `60 / 180 ≈ 0,33`. В коде пересечение считается по координатам двух углов: берём больший левый верхний и меньший правый нижний угол, обрезаем отрицательную ширину или высоту до нуля. Ошибка центра здесь 6 пикселей, поэтому на этот кадр можно ответить «да» по P20 и «нет» по IoU ≥ 0,5.

**Как получается строка общей таблицы.** `evaluate.py` сначала считает метрики отдельно по каждому видео. Потом усредняет P20, AUC, долю IoU ≥ 0,5 и средний IoU с одинаковым весом для всех шести видео. Так фрагмент из 500 кадров не получает больше веса при оценке качества, чем `uav3` из 265. Число срывов складывается. Скорость считается по сумме обновлений и сумме замеров. Например, в `test` 2 650 кадров, из них шесть первых идут на инициализацию. В знаменателе FPS суммарное время **2 644** вызовов `update`. Кадры без правильной разметки влияют на время прогона, хотя в метрики качества не попадают.

**Что на самом деле покрывают пять тестов кода.** Первый проверяет пограничные значения IoU и P20 и разрыв срыва кадром без разметки. Второй проверяет ошибку при несовпадении числа рамок и при полностью отсутствующей валидной разметке. Третий сдвигает известный искусственный объект на `(4, 3)` и проверяет, что LK сдвинул рамку без изменения её размеров. Четвёртый проверяет, что три трекера OpenCV можно создать, инициализировать и вызвать. Пятый проверяет пересчёт координат на изображении с нечётными размерами. Качество на реальных роликах смотрим отдельно по таблицам эксперимента.

## Как запустить у себя

### Уже есть текущая папка на компьютере

Из PowerShell зайди в проект и возьми его локальный Python. Всё ниже запускается из папки `iz1`.

```powershell
Set-Location 'D:\code\openCV\iz1'
$python = '.\.venv310\Scripts\python.exe'
& $python -m unittest discover -s tests -v
& $python evaluate.py --split test --methods CSRT KCF MOSSE LK STUDENT
```

Первая команда с `$python` прогонит проверки кода. Вторая возьмёт сохранённые ответы и `data/test/.../groundtruth.csv`, пересчитает метрики и выведет сводку. Для показа преподавателю проще заранее открыть готовые [графики](results/test/success.png) и [видео `car2`](results/test/videos/car2_STUDENT.mp4).

### Распаковал ZIP или хочешь заново пройти весь процесс

В комплекте уже есть графики, видео и таблицы. Если хочешь их только посмотреть, распакуй ZIP и открой `results/`. Для пересчёта и запуска нужны Python 3.10, зависимости и входные кадры. Здесь считаем, что `python` в текущем PowerShell указывает на Python 3.10. Проверь `python --version` перед созданием окружения.

```powershell
python -m venv .venv310
$python = '.\.venv310\Scripts\python.exe'
& $python -m pip install -r requirements.txt
& $python -m unittest discover -s tests -v
```

Чтобы начать с подбора на `dev`, подготовь данные. Можно выбрать команду для локального ZIP или для частичной загрузки.

```powershell
& $python prepare_data.py --archive 'D:\путь\Dataset_UAV123.zip' --split dev
# Или скачать только нужные данные
& $python prepare_data.py --download --split dev
```

После подготовки запусти цепочку. `run_trackers.py --split dev` по умолчанию прогоняет четыре базовых метода. Свой метод и таблицы подбора появятся после `robustness.py --tune`.

```powershell
& $python audit.py
& $python run_trackers.py --split dev
& $python robustness.py --tune
& $python evaluate.py --split dev --methods CSRT KCF MOSSE LK STUDENT
& $python report.py --split dev --video-mode examples
```

В готовом комплекте `submission.json` и результаты `test` уже есть. Чтобы только пересчитать тестовые метрики после распаковки, сначала восстанови входы через `prepare_data.py --download --split test` или подставь локальный ZIP через `--archive`, затем запусти `evaluate.py --split test --methods CSRT KCF MOSSE LK STUDENT`.

Если повторяешь **весь** эксперимент с нуля, работай в отдельной копии исходников с чистой папкой `results/test` и без старого `submission.json`. После выбора параметра на `dev` подготовь `test`, зафиксируй решение, затем прогоняй тест.

```powershell
& $python prepare_data.py --download --split test
& $python audit.py --freeze submission.json
& $python run_trackers.py --split test --methods CSRT KCF MOSSE LK STUDENT --frozen submission.json
& $python evaluate.py --split test --methods CSRT KCF MOSSE LK STUDENT
& $python report.py --split test --video-mode examples
```

## Что у нас получилось и что сказать, если спросят «почему так»

На `dev` мы выбрали `1,10`: доля кадров с IoU ≥ 0,5 выросла с **29,3% у LK** до **49,5% у STUDENT**. Для STUDENT при яркости 70% получили **51,4%**, при уменьшении разрешения до 75% — **44,1%**. Так получилось на этих шести фрагментах. [Подбор](results/dev/tuning.csv), [устойчивость](results/dev/robustness.csv)

На `test` лучший **CSRT**: **P20 0,767**, **AUC 0,412**, **40,9% кадров с IoU ≥ 0,5**, **16,8 обновления/с**. STUDENT показал **11,6%** против **14,9%** у обычного LK. Удобный пример — [`car2`](results/test/failures/car2_STUDENT_000153.png). На кадре 153 эталон был 33 × 32, а предсказание — примерно 135 × 79 пикселей. Точки фона мы отдельно не размечали, поэтому это гипотеза. [Итоговые метрики](results/test/summary.csv)

Ещё два примера на случай вопросов. На [`truck2`](results/test/events/truck2_140_175_210.png) башня действительно частично закрывает машину около кадра 175, но срыв MOSSE начался на кадре 6. Значит, сам этот срыв нельзя объяснить башней. А [`uav3`](results/test/events/uav3_1_97_121.png) хорошо показывает, зачем нужны обе метрики: для рамки 12 × 10 сдвиг всего на 6 пикселей даёт IoU примерно 0,33, хотя в P20 такой кадр засчитается.

### Если преподаватель пойдёт глубже

- **«Это обучение модели?»** У готовых фильтров есть внутренняя адаптация во время трекинга. В нашем эксперименте на `dev` мы выбирали внешний параметр варианта LK. На `test` подбора не было. Для нового видео трекер создаётся заново и получает его начальную рамку.
- **«Почему именно 1,10, если при 1,06 срывов меньше?»** До теста мы выбрали критерий — наибольшая доля кадров с IoU ≥ 0,5. Для 1,06 она была 45,5% при пяти срывах, для 1,10 — 49,5% при семи. Срывы считаются эпизодами, а доля учитывает отдельные кадры. При другом критерии выбор мог бы отличаться. [Три варианта](results/dev/tuning.csv)
- **«Какое число кадров у вас получилось по каждому методу?»** В итоговом `test` сохранено 2 650 строк с рамками или пропусками на каждый метод. Из них шесть строк — начальные рамки, поэтому замеров `update` 2 644. Качество считается отдельно по видео, с исключением кадров без валидного эталона.
- **«Почему AUC примерно похож на средний IoU, но числа не равны?»** Средний IoU сразу усредняет покадровые IoU. AUC в нашем коде берёт среднее success по конечной сетке из 21 порога. При строгом `>` IoU ровно 1,0 не проходит порог 1,0, например. Поэтому даже идеальный трекер дал бы по этой формуле `20/21 ≈ 0,952`.
- **«Что поменял бы дальше?»** Проверил бы на `dev`, выдерживает ли метод ограничение на накопленный размер и помогает ли отбрасывать точки возле фона или после слабого совпадения. Это продолжение эксперимента. Текущие выводы основаны на уже проведённой проверке.
- **«За что отвечал каждый участник?»** Перед защитой подготовьте по одному конкретному ответу про свой фактический вклад. Здесь в отчёте у обоих оставлены поля для уточнения.

Если надо объяснить всё за полминуты своими словами: «На первом кадре задаём объект, дальше сравниваем, как пять методов держат его рамку без подсказок. У Лукаса–Канаде базовая рамка только двигается, а мы проверили, поможет ли менять её размер по движению точек. На `dev` стало лучше, на `test` эффект не перенёсся. В итоге для наших видео лучше всего сработал CSRT. По картинкам можно показать, где теряется центр, а где проблема в размере рамки».
